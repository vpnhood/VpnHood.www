SERVER since v9.1.864, its first release on .NET 11. The distributions are those .NET 11 supports (supported-os.md in dotnet/core, glibc 2.27 on x64 and arm64), plus Amazon Linux and Arch; a version we did not test is listed on that support, and fixed if someone reports it (owner, 2026-11-03). Tested 2026-11-03 with v9.1.864's own install command, each to its service, its TUN adapter with NAT, and TCP 443: the Debian 13 cloud image as a VPS gets it (it had no ICU; the installer added it), and in systemd containers Ubuntu 22.04, 24.04, 26.04, Debian 12, 13, AlmaLinux 8, 9, 10, Rocky 9, CentOS Stream 10, Amazon Linux 2023, openSUSE Leap 16.0, Fedora 45 and Arch. Alpine installs but cannot run the glibc build. Windows: Windows 11 Pro without Hyper-V answers New-NetNat with "Invalid class", so the server ran as a proxy; the Containers feature did not bring WinNAT, Hyper-V did. Windows Server 2025 had WinNAT with neither. Names and versions are markup, as there is nothing in them to translate; the versions are dir="ltr", or an RTL page turns their list around. The processor requirement is a card, edged in the warning ink with its own art, as it is the one that stops a server on hardware that passes the rest: since v9.1.864 the server runs on .NET 11, which refuses to start on an x64 processor below x86-64-v2 (CX16, POPCNT, SSE3, SSSE3, SSE4.1, SSE4.2), prints cpu_error and exits, and systemd restarts it forever. A VPS whose host gives it QEMU's basic kvm64 model hides them all, whatever the hardware. ARM64's minimum did not change. The check greps two of the six flags: kvm64 lacks every one, and a real processor with SSE4.2 and POPCNT has the rest.
